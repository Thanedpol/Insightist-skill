# Data Cleaning Playbook

Skill นี้ช่วยแปลงชุดข้อมูลดิบที่ "รก" ให้กลายเป็นข้อมูลที่พร้อมนำไปวิเคราะห์หรือใช้ต่อในโมเดล โดยจัดการปัญหาข้อมูล 4 ประเภทหลักที่พบบ่อยที่สุด ได้แก่ ค่าที่หายไป (missing values), แถวซ้ำ (duplicates), ค่าผิดปกติ (outliers) และรูปแบบที่ไม่สอดคล้องกัน (inconsistent format) เหมาะสำหรับนักวิเคราะห์ข้อมูล, data scientist หรือใครก็ตามที่ต้องเตรียมข้อมูลก่อนทำ dashboard, รายงาน หรือ machine learning

จุดเด่นของ skill นี้คือไม่ใช่แค่ "ลบทิ้ง" หรือ "แก้เงียบๆ" แต่ทุกการตัดสินใจต้องมีเหตุผลรองรับและถูกบันทึกไว้ในสรุปท้ายสุด เพื่อให้คนอื่นตรวจสอบย้อนหลังได้ว่าทำไมข้อมูลถึงเปลี่ยนจากต้นฉบับ

## เมื่อไหร่ควรใช้ skill นี้

- ก่อนนำข้อมูลดิบ (CSV, Excel, export จากระบบ) ไปทำ dashboard หรือ report
- เมื่อเจอปัญหาตัวเลขสรุปไม่ตรงกัน ยอดรวมผิดปกติ หรือ dashboard แสดงผลแปลกๆ
- เมื่อรวมข้อมูลจากหลายแหล่ง (เช่น หลายสาขา, หลายระบบ) ที่ format ไม่ตรงกัน
- ก่อนนำข้อมูลเข้าโมเดล machine learning หรือทำ statistical analysis
- เมื่อผู้ใช้อัปโหลดไฟล์ข้อมูลแล้วบอกว่า "ยังไม่ได้เช็คเลย" หรือ "ข้อมูลดิบๆ"
- เมื่อต้องทำ data audit หรือ data quality check เป็นระยะ

## ขั้นตอนการทำงาน

1. **สำรวจข้อมูลเบื้องต้น (data profiling)** — ดูจำนวนแถว/คอลัมน์ ชนิดข้อมูลแต่ละคอลัมน์ (ตัวเลข/ข้อความ/วันที่) ค่าตัวอย่าง 5-10 แถวแรก และสถิติเบื้องต้น (min/max/mean สำหรับตัวเลข, unique values สำหรับข้อความ) เพื่อรู้ภาพรวมก่อนแก้อะไร
2. **จัดการ Missing Values** — เช็คทีละคอลัมน์ว่ามีค่าว่าง/null กี่เปอร์เซ็นต์ แล้วเลือกวิธีจัดการตามกฎนี้:
   - ถ้าคอลัมน์มีค่าว่างเกิน 60-70% ของทั้งหมด ให้พิจารณาตัดคอลัมน์ทิ้งทั้งคอลัมน์ (แจ้งเหตุผลเสมอ)
   - ถ้าแถวใดขาดข้อมูลในคอลัมน์ที่สำคัญมาก (เช่น primary key, วันที่ทำรายการ) ให้พิจารณาตัดแถวทิ้ง
   - ถ้าเป็นตัวเลขและค่าว่างมีสัดส่วนน้อย ให้เติมด้วยค่ากลาง (median สำหรับข้อมูลเบ้/มี outlier, mean สำหรับข้อมูลกระจายปกติ) หรือใช้ 0 ถ้าค่าว่าง = ไม่มีจริงๆ (เช่น ยอดขาย)
   - ถ้าเป็นข้อความ/หมวดหมู่ ให้เติมด้วยค่าที่พบบ่อยที่สุด (mode) หรือ label ว่า "ไม่ระบุ/Unknown" หากไม่ควรเดา
   - ห้ามเติมค่าแบบเดาสุ่มโดยไม่มีเหตุผลทางสถิติหรือ business logic รองรับ
3. **จัดการ Duplicates** — หาแถวที่ซ้ำกันโดย:
   - เช็คซ้ำแบบ exact match (ทุกคอลัมน์เหมือนกันทุกตัว) — ลบออกได้เกือบทุกกรณี เก็บไว้ 1 แถว
   - เช็คซ้ำแบบ key-based (เช่น เลข order เดียวกัน หรือ email เดียวกัน) แต่ค่าคอลัมน์อื่นต่างกัน — ต้องตัดสินใจว่าจะเก็บแถวล่าสุด (ตาม timestamp) หรือรวมข้อมูล (merge) ไม่ใช่ลบมั่ว
   - ระวัง false duplicate เช่น ชื่อคนซ้ำกันจริงแต่เป็นคนละคน (ต้องเช็ค key อื่นประกอบ เช่น เลขบัตร/email)
4. **จัดการ Outliers** — หาค่าผิดปกติในคอลัมน์ตัวเลขด้วยวิธีใดวิธีหนึ่ง:
   - IQR method: ค่าที่ต่ำกว่า Q1 - 1.5×IQR หรือสูงกว่า Q3 + 1.5×IQR ถือเป็น outlier
   - Z-score: ค่าที่ห่างจากค่าเฉลี่ยเกิน 3 standard deviation
   - เมื่อเจอ outlier ต้องแยกให้ออกว่าเป็น "ข้อมูลผิดพลาดจากการกรอก" (เช่น อายุ 999 ปี, ราคาติดลบที่ไม่ควรติดลบ) ควรแก้ไขหรือตัดทิ้ง, หรือเป็น "ค่าจริงที่ผิดปกติแต่ถูกต้อง" (เช่น ยอดขายพุ่งช่วงโปรโมชัน) ควรเก็บไว้แต่ทำเครื่องหมายไว้เพื่อไม่ให้บิดเบือนค่าเฉลี่ยโดยไม่รู้ตัว
   - ห้ามลบ outlier ทิ้งอัตโนมัติโดยไม่ตรวจสอบที่มาก่อน
5. **แก้ไข Inconsistent Format** — ตรวจและปรับให้เป็นมาตรฐานเดียวกัน:
   - รูปแบบวันที่ (เช่น 01/02/2025 vs 2025-02-01) ให้แปลงเป็นรูปแบบเดียว (แนะนำ ISO 8601: YYYY-MM-DD)
   - ตัวพิมพ์เล็ก/ใหญ่และช่องว่างเกิน (เช่น "bangkok", "Bangkok ", "BANGKOK") ให้ trim และปรับ casing ให้เหมือนกัน
   - หน่วยไม่ตรงกัน (เช่น กิโลกรัม vs กรัม, บาท vs ดอลลาร์) ให้แปลงเป็นหน่วยเดียวกันทั้งชุดข้อมูล และบันทึกอัตราแปลงที่ใช้
   - ค่าหมวดหมู่ที่สะกดต่างกันแต่ความหมายเดียวกัน (เช่น "กทม.", "กรุงเทพ", "Bangkok") ให้รวมเป็นค่ามาตรฐานเดียว
   - ชนิดข้อมูลผิด (ตัวเลขถูกเก็บเป็น text เพราะมีคอมมาแทรก เช่น "1,200") ให้แปลงชนิดข้อมูลให้ถูกต้อง
6. **ตรวจสอบซ้ำ (validation pass)** — หลังทำความสะอาดแล้ว เช็คอีกรอบว่าจำนวนแถว/ผลรวมสำคัญ (เช่น ยอดขายรวม) ยังสมเหตุสมผล ไม่หายไปมากผิดปกติเมื่อเทียบกับข้อมูลต้นฉบับ
7. **สรุปสิ่งที่ทำและเหตุผล** — เขียน log การเปลี่ยนแปลงทุกขั้นตอน (ก่อน/หลัง เป็นตัวเลข) พร้อมเหตุผลของแต่ละการตัดสินใจ เพื่อให้ตรวจสอบย้อนหลังได้

## โครงสร้าง Output

```
# สรุปการทำความสะอาดข้อมูล: [ชื่อไฟล์/ชุดข้อมูล]

## ภาพรวมก่อน-หลัง
| รายการ | ก่อนทำความสะอาด | หลังทำความสะอาด |
|---|---|---|
| จำนวนแถว | ... | ... |
| จำนวนคอลัมน์ | ... | ... |
| จำนวน missing values | ... | ... |
| จำนวนแถวซ้ำ | ... | ... |

## สิ่งที่ทำและเหตุผล

### 1. Missing Values
- คอลัมน์ [ชื่อ]: [วิธีจัดการ] เพราะ [เหตุผล]

### 2. Duplicates
- พบ [จำนวน] แถวซ้ำแบบ [exact/key-based] — [วิธีจัดการ] เพราะ [เหตุผล]

### 3. Outliers
- คอลัมน์ [ชื่อ]: พบค่าผิดปกติ [รายละเอียด] — [เก็บไว้/แก้ไข/ตัดทิ้ง] เพราะ [เหตุผล]

### 4. Inconsistent Format
- คอลัมน์ [ชื่อ]: [ปัญหาที่พบ] → ปรับเป็น [มาตรฐานใหม่] เพราะ [เหตุผล]

## จุดที่ควรระวังต่อ (ถ้ามี)
- [ข้อมูลที่ไม่แน่ใจ ต้องให้เจ้าของข้อมูลยืนยัน]

## ข้อมูลพร้อมใช้งานแล้ว
[สรุปสั้นๆ ว่าตอนนี้ข้อมูลอยู่ในสถานะไหน ใช้ต่อกับอะไรได้บ้าง]
```

## ตัวอย่าง

**Input** (ตัวอย่างข้อมูลลูกค้าดิบ 5 แถว):

```
id, name,      city,      signup_date, amount
1,  Somsak ,   Bangkok,   2025-01-05,  1200
2,  somsak,    bangkok,   2025-01-05,  1200
3,  Malee,     กทม.,      05/01/2025,  980
4,  Wichai,    Chiang Mai, 2025-01-06, 
5,  Anong,     Bangkok,   2025-01-07,  99999
```

**Output คร่าวๆ ที่ควรได้:**

```
## ภาพรวมก่อน-หลัง
| รายการ | ก่อน | หลัง |
|---|---|---|
| จำนวนแถว | 5 | 4 |
| missing values | 1 (amount แถว 4) | 0 |
| แถวซ้ำ | 1 (id 1-2) | 0 |

## สิ่งที่ทำและเหตุผล
### 1. Missing Values
- คอลัมน์ amount แถว id=4: เติมด้วยค่า median ของคอลัมน์ (1200) เพราะเป็นค่าว่างเดี่ยวและข้อมูลมีจำนวนน้อยเกินกว่าจะตัดแถวทิ้ง

### 2. Duplicates
- พบแถว id=1 และ id=2 เป็นคนเดียวกัน (ชื่อ "Somsak "/"somsak" ต่างแค่ตัวพิมพ์และช่องว่าง, เมืองและวันที่ตรงกัน) — เก็บ id=1 ลบ id=2 เพราะข้อมูลซ้ำซ้อนกันทุกฟิลด์เชิงความหมาย

### 3. Outliers
- คอลัมน์ amount แถว id=5: ค่า 99999 สูงกว่าปกติมาก (ค่าอื่นอยู่ราว 980-1200) — ทำเครื่องหมายไว้ให้ตรวจสอบกับเจ้าของข้อมูลก่อนตัดสินใจ ยังไม่ลบทิ้งเพราะอาจเป็นยอดสั่งซื้อพิเศษจริง

### 4. Inconsistent Format
- คอลัมน์ city: "กทม." แปลงเป็น "Bangkok" ให้ตรงกับค่าอื่น
- คอลัมน์ signup_date: "05/01/2025" แปลงเป็น "2025-01-05" (ISO 8601)

## จุดที่ควรระวังต่อ
- ยอด 99999 ของ Anong ควรยืนยันกับทีมขายก่อนใช้ในรายงานสรุป
```

## เกณฑ์คุณภาพ

- [ ] ครอบคลุมทั้ง 4 ปัญหาหลัก (missing values, duplicates, outliers, inconsistent format) ไม่ข้ามข้อใดข้อหนึ่งโดยไม่ตรวจสอบ
- [ ] ทุกการแก้ไข/ลบข้อมูล มีเหตุผลกำกับชัดเจน ไม่ใช่ทำเงียบๆ
- [ ] มีตารางเปรียบเทียบก่อน-หลังเป็นตัวเลขที่ตรวจสอบได้
- [ ] แยกแยะ outlier ที่ "ผิดพลาดจริง" กับ "ค่าจริงที่ผิดปกติ" ก่อนตัดสินใจ ไม่ลบทิ้งอัตโนมัติ
- [ ] ระบุจุดที่ไม่แน่ใจและต้องให้เจ้าของข้อมูลยืนยันแยกออกมาให้ชัด
- [ ] ผลลัพธ์สุดท้ายพร้อมนำไปใช้งานต่อได้จริงโดยไม่ต้องแก้เพิ่ม
