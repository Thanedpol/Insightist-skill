# Code Review Checklist

Skill นี้ช่วย "ตรวจโค้ด" แบบมีมาตรฐานเดียวกันทุกครั้ง ไม่ว่าโค้ดจะเป็นภาษาอะไร โดยมองผ่าน 4 มุมหลักที่ทีมพัฒนาซอฟต์แวร์ทั่วไปให้ความสำคัญ ได้แก่ readability (อ่านง่าย/ดูแลง่าย), security (ความปลอดภัย), performance (ประสิทธิภาพ) และ test coverage (การทดสอบ) เหมาะสำหรับนักพัฒนา, tech lead, หรือใครก็ตามที่ต้องรีวิว pull request แต่ไม่อยากรีวิวแบบสุ่มดูผ่านๆ

ผลลัพธ์ที่ได้ไม่ใช่แค่ "list ปัญหา" แต่เป็น review comment ที่สร้างสรรค์ — บอกว่าอะไรดีอยู่แล้ว อะไรควรแก้ ทำไมถึงควรแก้ และแก้อย่างไร เพื่อให้คนเขียนโค้ดรู้สึกว่าถูกช่วยเหลือ ไม่ใช่ถูกตัดสิน

## เมื่อไหร่ควรใช้ skill นี้

- ก่อน merge pull request หรือ commit เข้า branch หลัก
- เมื่อผู้ใช้แปะโค้ด/diff มาแล้วถามว่า "โอเคไหม", "มีอะไรต้องแก้ไหม"
- เมื่อต้องการ second opinion ก่อนส่งงานให้ลูกค้าหรือทีมอื่น
- เมื่อรับช่วงต่อโค้ดจากคนอื่น (onboarding, code handover) แล้วอยากรู้จุดเสี่ยง
- เมื่อสงสัยว่าโค้ดมีช่องโหว่ความปลอดภัย หรือมีจุดที่จะทำให้ระบบช้า
- เมื่อทำ refactor ใหญ่แล้วอยากเช็คว่าไม่ทำลาย coverage หรือ pattern เดิม

## ขั้นตอนการทำงาน

1. **ทำความเข้าใจ context ก่อน** — อ่านว่าโค้ดนี้ทำหน้าที่อะไร ภาษา/framework อะไร เป็นไฟล์เดี่ยวหรือ diff ของ PR ถ้ามี PR description หรือ ticket ให้อ่านประกอบเพื่อรู้ intent ที่แท้จริง
2. **ตรวจ Readability** — เช็คตามหัวข้อย่อยนี้:
   - ชื่อตัวแปร/ฟังก์ชัน/คลาส สื่อความหมายชัดเจน ไม่ใช้ชื่อกำกวม (`data`, `temp`, `x2`)
   - ฟังก์ชันทำหน้าที่เดียว (single responsibility) ไม่ยาวเกิน ~40-50 บรรทัดโดยไม่มีเหตุผล
   - ไม่มี magic number/string ที่ควรเป็น constant
   - โครงสร้าง (indentation, nesting) อ่านง่าย ไม่ nest if/for เกิน 3-4 ชั้น
   - comment อธิบาย "ทำไม" ไม่ใช่ทวนสิ่งที่โค้ดบอกอยู่แล้ว
   - ไม่มีโค้ดซ้ำซ้อน (DRY) ที่ควร extract เป็นฟังก์ชันร่วม
3. **ตรวจ Security** — เช็คตามหัวข้อย่อยนี้:
   - Input จากผู้ใช้ (form, API param, query string) ผ่านการ validate/sanitize ก่อนใช้งาน
   - ไม่มี SQL/command/query ที่ต่อ string ตรงๆ จาก input (เสี่ยง injection) — ต้องใช้ parameterized query
   - ไม่มี secret/API key/password ฝังอยู่ในโค้ด (hardcoded credentials)
   - จัดการ error/exception อย่างเหมาะสม ไม่ leak stack trace หรือข้อมูล internal ออกไปให้ผู้ใช้เห็น
   - สิทธิ์การเข้าถึง (authorization) ถูกเช็คในทุก endpoint ที่ควรเช็ค ไม่ใช่เช็คแค่ฝั่ง UI
   - dependency ภายนอกที่เพิ่มเข้ามาไม่มีช่องโหว่ที่รู้จักและมาจากแหล่งน่าเชื่อถือ
4. **ตรวจ Performance** — เช็คตามหัวข้อย่อยนี้:
   - ไม่มี loop ซ้อน loop (O(n²) ขึ้นไป) ที่ไม่จำเป็นบนข้อมูลขนาดใหญ่
   - ไม่ query database ซ้ำในลูป (N+1 query problem) ควร batch หรือ join แทน
   - มีการใช้ cache/memoization ในจุดที่คำนวณซ้ำๆ ด้วย input เดิม
   - ไม่โหลดข้อมูลทั้งหมดเข้าหน่วยความจำโดยไม่จำเป็น (ควร stream/paginate)
   - resource ที่เปิดไว้ (file handle, connection) ถูกปิดอย่างถูกต้องเสมอ (try/finally หรือ context manager)
5. **ตรวจ Test Coverage** — เช็คตามหัวข้อย่อยนี้:
   - มี unit test ครอบคลุม happy path และ edge case หลักๆ (ค่าว่าง, ค่าลบ, ค่าเกินขอบเขต)
   - Logic ที่ซับซ้อนหรือมีความเสี่ยงสูง (คำนวณเงิน, สิทธิ์การเข้าถึง) มี test เจาะจง
   - ไม่มี test ที่ assert หลวมเกินไปจนไม่จับ regression ได้จริง (เช่น assert แค่ไม่ throw error)
   - เพิ่มโค้ดใหม่แล้ว test เดิมยังผ่านหมด ไม่ต้อง skip/comment ทิ้ง
6. **จัดลำดับความสำคัญ** — แบ่งข้อค้นพบเป็น 3 ระดับ: 🔴 Critical (ต้องแก้ก่อน merge เช่นช่องโหว่ความปลอดภัย), 🟡 Suggested (ควรแก้แต่ไม่บล็อก), 🟢 Nitpick (เรื่องเล็กน้อย สไตล์ส่วนตัว)
7. **เขียน review comment แบบสร้างสรรค์** — ทุกจุดที่ชี้ปัญหา ให้บอกด้วยว่า "ทำไมถึงเป็นปัญหา" และ "แก้อย่างไร" พร้อมชมจุดที่ทำดีอยู่แล้วอย่างน้อย 1 จุด เพื่อให้ feedback สมดุล
8. **สรุปผลรวม** — ให้คำแนะนำท้ายสุดว่า "พร้อม merge", "merge ได้แต่ควรตามแก้ทีหลัง", หรือ "ควรแก้ก่อน merge" พร้อมเหตุผลสั้นๆ

## ตัวอย่าง

**Input** (ฟังก์ชัน Python ที่ผู้ใช้แปะมาให้รีวิว):

```python
def get_user_orders(user_id):
    query = "SELECT * FROM orders WHERE user_id = " + user_id
    result = db.execute(query)
    orders = []
    for r in result:
        orders.append(r)
    return orders
```

```
## จุดที่ทำได้ดี
- ชื่อฟังก์ชัน get_user_orders สื่อความหมายชัดเจน อ่านแล้วรู้เลยว่าทำอะไร

## ข้อค้นพบ

### 🔴 Critical
1. **SQL Injection** — บรรทัด 2
   - ปัญหา: ต่อ string user_id เข้า query ตรงๆ โดยไม่ sanitize
   - ทำไมถึงสำคัญ: ผู้ใช้ส่ง user_id เป็น "1 OR 1=1" ได้ ทำให้ดึงข้อมูลของทุกคนออกมา
   - ข้อเสนอแนะ: ใช้ parameterized query เช่น
     db.execute("SELECT * FROM orders WHERE user_id = %s", (user_id,))

### 🟡 Suggested
1. **Loop ที่ไม่จำเป็น** — บรรทัด 4-6
   - ปัญหา: ใช้ for loop เพื่อ copy ค่าจาก result ไปยัง list เปล่าๆ
   - ข้อเสนอแนะ: เขียนเป็น return list(result) ได้เลย สั้นและอ่านง่ายกว่า

## คำแนะนำสุดท้าย
ควรแก้ก่อน merge — มีช่องโหว่ SQL injection ที่กระทบความปลอดภัยของระบบโดยตรง
```

## เกณฑ์คุณภาพ

- [ ] ครอบคลุมทั้ง 4 มุม (readability, security, performance, test coverage) ไม่ข้ามมุมใดมุมหนึ่ง
- [ ] ทุกข้อค้นพบมีระดับความสำคัญ (Critical/Suggested/Nitpick) ชัดเจน
- [ ] ทุกปัญหาที่ชี้ มาพร้อมคำอธิบาย "ทำไม" และ "แก้อย่างไร" ไม่ใช่แค่บอกว่าผิด
- [ ] มีการชมจุดที่ทำดีอย่างน้อย 1 จุด เพื่อให้ feedback สร้างสรรค์ ไม่ใช่จับผิดอย่างเดียว
- [ ] มีคำแนะนำสุดท้ายที่ตัดสินใจได้จริง (merge ได้ไหม)
- [ ] ไม่มีตัวอย่างโค้ดที่เป็นอันตราย/exploit จริง ใช้เพื่ออธิบายปัญหาเชิงการศึกษาเท่านั้น
