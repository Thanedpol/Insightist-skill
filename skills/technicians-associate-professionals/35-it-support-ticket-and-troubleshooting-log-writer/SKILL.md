# IT Support Ticket and Troubleshooting Log Writer

Skill นี้ช่วยแปลงบันทึกการแจ้งปัญหาและการแก้ไขปัญหาไอที ให้กลายเป็น ticket และ log ที่มีโครงสร้างชัดเจน ค้นหาย้อนหลังได้ และนำไปใช้เป็นฐานความรู้ (knowledge base) สำหรับปัญหาที่เกิดซ้ำได้ เหมาะกับงานสายช่างเทคนิคสารสนเทศและการสื่อสารที่ต้องบันทึกทุกขั้นตอนการวินิจฉัยและแก้ไขอย่างเป็นระบบ

## เมื่อไหร่ควรใช้ skill นี้

- เจ้าหน้าที่ IT Support/Helpdesk รับแจ้งปัญหาจากผู้ใช้งานแล้วต้องการเปิด ticket ให้ครบข้อมูล
- ช่างเทคนิคเครือข่ายต้องการบันทึกขั้นตอนการวินิจฉัยปัญหาเครือข่ายและวิธีแก้ไขที่ใช้ได้ผล
- ช่างเทคนิคปฏิบัติการไอทีต้องการสรุปเหตุขัดข้องของระบบ (incident) หลังแก้ไขเสร็จ เพื่อทำเป็นเอกสารอ้างอิง
- ช่างเทคนิควิศวกรรมโทรคมนาคมต้องการบันทึกการแก้ไขปัญหาระบบสัญญาณหรืออุปกรณ์สื่อสาร
- ช่างเทคนิคกระจายเสียงและโสตทัศนูปกรณ์ต้องการบันทึกปัญหาอุปกรณ์และวิธีแก้ไขเพื่อใช้อ้างอิงครั้งต่อไป

## ขั้นตอนการทำงาน

### 1. รวบรวมข้อมูลการแจ้งปัญหา (ticket intake)
บันทึก: ผู้แจ้ง, วันที่/เวลาที่แจ้ง, ระบบ/อุปกรณ์ที่มีปัญหา, อาการที่ผู้ใช้งานพบ (ตามคำบอกเล่า), ระดับความเร่งด่วน/ผลกระทบต่องาน

### 2. จัดหมวดปัญหาและระดับความสำคัญ
ระบุประเภทปัญหา (เช่น ฮาร์ดแวร์, ซอฟต์แวร์, เครือข่าย, สิทธิ์การเข้าถึง) และระดับความสำคัญ (วิกฤต/สูง/ปานกลาง/ต่ำ) ตามผลกระทบต่อผู้ใช้งานหรือธุรกิจ

### 3. บันทึกขั้นตอนการวินิจฉัย (diagnosis steps)
เรียงลำดับสิ่งที่ตรวจสอบจริง เช่น ตรวจ log, ทดสอบการเชื่อมต่อ, ตรวจสอบการตั้งค่า — ระบุผลของแต่ละขั้นตอนตามที่ตรวจพบจริง ไม่เดาสาเหตุที่ยังไม่ได้ตรวจสอบ

### 4. ระบุสาเหตุที่แท้จริง (root cause)
สรุปสาเหตุของปัญหาจากหลักฐานที่ตรวจพบ หากยังไม่สามารถระบุสาเหตุแน่ชัดได้ ให้ระบุตรงไปตรงมาว่า "ยังไม่สามารถระบุสาเหตุแน่ชัด" แทนการเดา

### 5. บันทึกวิธีแก้ไขที่ใช้จริง (resolution steps)
ระบุขั้นตอนที่ทำเพื่อแก้ไขปัญหา ผลลัพธ์หลังแก้ไข และเวลาที่ใช้ในการแก้ไข

### 6. เขียนเป็นบันทึกความรู้ (knowledge-base entry) ถ้าปัญหานี้อาจเกิดซ้ำ
สรุปอาการ สาเหตุ และวิธีแก้ไขให้เป็นรูปแบบที่ค้นหาและนำไปใช้ซ้ำได้ง่ายสำหรับทีมสนับสนุน

### 7. ปิด ticket และระบุการติดตามผล
ระบุสถานะสุดท้าย (ปิดแล้ว/รอติดตาม/ส่งต่อทีมอื่น) และสิ่งที่ต้องติดตามต่อถ้ามี เช่น การเฝ้าระวังไม่ให้ปัญหากลับมาเกิดซ้ำ

## โครงสร้าง Output

```
=== IT Support Ticket / Troubleshooting Log ===
หมายเลข Ticket: [ถ้ามี]
ผู้แจ้ง: [ชื่อ/แผนก]
วันที่แจ้ง: [วัน/เดือน/ปี เวลา]
ระบบ/อุปกรณ์: [...]
ระดับความสำคัญ: [วิกฤต/สูง/ปานกลาง/ต่ำ]

1) อาการที่พบ (ตามคำแจ้ง)
   [...]

2) ขั้นตอนการวินิจฉัย
   - [ขั้นตอนที่ตรวจสอบ] → ผล: [...]

3) สาเหตุที่แท้จริง (Root Cause)
   [สรุปจากหลักฐาน หรือ "ยังไม่สามารถระบุสาเหตุแน่ชัด"]

4) วิธีแก้ไขที่ใช้ (Resolution)
   - [ขั้นตอนที่ทำ] → ผลลัพธ์: [...]
   เวลาที่ใช้แก้ไข: [...]

5) บันทึกความรู้ (Knowledge Base Entry) — ถ้าเกิดซ้ำได้
   อาการ: [...] | สาเหตุ: [...] | วิธีแก้: [...]

6) สถานะปิดงาน
   สถานะ: [ปิดแล้ว/รอติดตาม/ส่งต่อทีมอื่น]
   สิ่งที่ต้องติดตามต่อ: [...]
```

## ตัวอย่าง

**Input:** พนักงานแจ้งว่าเข้าใช้อีเมลบริษัทไม่ได้ตั้งแต่เช้า เจ้าหน้าที่ IT ตรวจสอบพบว่ารหัสผ่านหมดอายุตามนโยบายบริษัท จึงรีเซ็ตรหัสผ่านและแจ้งพนักงานตั้งรหัสใหม่

**Output (คร่าวๆ):**
- อาการที่พบ: เข้าใช้อีเมลบริษัทไม่ได้ตั้งแต่เช้า
- ขั้นตอนการวินิจฉัย: ตรวจสอบสถานะบัญชีผู้ใช้ในระบบ → พบสถานะ "รหัสผ่านหมดอายุ"
- สาเหตุที่แท้จริง: รหัสผ่านหมดอายุตามนโยบายความปลอดภัยของบริษัท (รอบ 90 วัน)
- วิธีแก้ไขที่ใช้: รีเซ็ตรหัสผ่านชั่วคราวและแจ้งพนักงานตั้งรหัสผ่านใหม่ตามนโยบาย → เข้าใช้งานได้ปกติ เวลาที่ใช้แก้ไข: 10 นาที
- สถานะปิดงาน: ปิดแล้ว ไม่มีสิ่งที่ต้องติดตามต่อ

## เกณฑ์คุณภาพ

- [ ] มีข้อมูลพื้นฐานของ ticket ครบ (ผู้แจ้ง เวลา ระบบที่มีปัญหา ระดับความสำคัญ)
- [ ] ขั้นตอนการวินิจฉัยเรียงตามลำดับจริงที่ตรวจสอบ พร้อมผลของแต่ละขั้นตอน
- [ ] ไม่เดาสาเหตุที่ยังไม่ได้ตรวจสอบหลักฐานจริง — ถ้าไม่แน่ใจให้ระบุว่ายังไม่สามารถระบุสาเหตุแน่ชัด
- [ ] วิธีแก้ไขที่บันทึกเป็นสิ่งที่ทำจริงและตรวจสอบผลลัพธ์ได้ ไม่ใช่คำแนะนำทั่วไปที่ยังไม่ได้ลองทำ
- [ ] ปัญหาที่มีแนวโน้มเกิดซ้ำถูกสรุปเป็นบันทึกความรู้ที่ค้นหาและนำไปใช้ต่อได้ง่าย
- [ ] ระบุสถานะปิดงานและสิ่งที่ต้องติดตามต่อชัดเจน
