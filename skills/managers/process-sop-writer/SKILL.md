---

# Process SOP Writer

Skill นี้ช่วยหัวหน้างาน เจ้าของธุรกิจ และทีมปฏิบัติการ เปลี่ยนคำอธิบายขั้นตอนงานที่พูดออกมาแบบสบายๆ ไม่เป็นระบบ ให้กลายเป็นเอกสาร SOP มาตรฐานที่พนักงานคนไหนอ่านแล้วก็ทำตามได้ทันที ลดการพึ่งพาความจำของคนคนเดียว ลดความผิดพลาดจากการสอนงานปากต่อปาก และทำให้ธุรกิจ scale ได้ง่ายขึ้นเมื่อรับคนใหม่

## เมื่อไหร่ควรใช้ skill นี้

- ผู้ใช้เล่าขั้นตอนการทำงานแบบพูดคุย ("ก็คือพอลูกค้าโทรมา เราก็...") แล้วอยากได้เป็นเอกสาร
- ผู้ใช้มีพนักงานคนเดียวที่รู้ขั้นตอนงานสำคัญ และอยากบันทึกไว้กันความรู้หายไปเมื่อคนลาออก
- ผู้ใช้กำลังจะรับพนักงานใหม่ และต้องการคู่มือ onboarding สำหรับตำแหน่งงานหนึ่งๆ
- ผู้ใช้มีขั้นตอนงานที่ทำผิดพลาดบ่อย อยากทำให้เป็นมาตรฐานเดียวกันทั้งทีม
- ผู้ใช้ต้องการเอกสารสำหรับตรวจสอบคุณภาพ (audit), ISO, หรือมาตรฐานองค์กรอื่นๆ ที่ต้องมี SOP เป็นลายลักษณ์อักษร
- ผู้ใช้ส่งบันทึกเสียงที่ถอดความแล้ว หรือแชทกลุ่มที่คุยขั้นตอนงานกัน แล้วขอให้จัดระเบียบเป็นเอกสาร

## ขั้นตอนการทำงาน

### 1. ทำความเข้าใจขั้นตอนงานดิบที่ผู้ใช้เล่ามา
อ่าน/ฟังเนื้อหาที่ผู้ใช้ให้มาอย่างละเอียด แล้วแยกแยะองค์ประกอบต่อไปนี้ออกจากคำพูดที่ไม่เป็นระบบ:
- จุดเริ่มต้นของกระบวนการ (trigger) — อะไรทำให้งานนี้เริ่มขึ้น
- จุดสิ้นสุด (end state) — งานเสร็จเมื่อไหร่ ผลลัพธ์คืออะไร
- ผู้เกี่ยวข้อง (roles) — ใครทำอะไรในแต่ละจุด
- เครื่องมือ/ระบบ/เอกสารที่ใช้ระหว่างทาง
- จุดตัดสินใจ (decision points) — ถ้า...ให้ทำอย่างนี้ ถ้าไม่...ให้ทำอีกอย่าง
- ข้อผิดพลาดที่พบบ่อยหรือสิ่งที่ผู้ใช้เน้นย้ำว่า "ห้ามลืม" หรือ "สำคัญมาก"

### 2. ถามคำถามเพิ่มเติมเฉพาะจุดที่ขาดหายและกระทบความปลอดภัย/ความถูกต้อง
ถ้าข้อมูลไม่พอที่จะเขียนขั้นตอนให้ทำตามได้จริง (เช่น ไม่รู้ว่าใครเป็นผู้อนุมัติ หรือไม่รู้ว่าเกิดข้อผิดพลาดแล้วต้องแจ้งใคร) ให้ถามสั้นๆ ตรงประเด็น อย่าถามเยอะเกินจำเป็นจนขัดจังหวะงาน ถ้าพอเดาได้อย่างมีเหตุผลจากบริบท ให้ระบุเป็น "สมมติฐานที่ควรยืนยัน" ในเอกสารแทนการหยุดถามทุกจุด

### 3. จัดโครงสร้างขั้นตอนเป็นลำดับที่ทำตามได้จริง
แปลงคำอธิบายให้เป็นขั้นตอนแบบเลขลำดับ (1, 2, 3, ...) โดยแต่ละขั้นตอนต้อง:
- ขึ้นต้นด้วยคำกริยาการกระทำ (เช่น "ตรวจสอบ...", "กรอก...", "ส่ง...", "แจ้ง...")
- มีความยาวพอดี ไม่รวมหลายการกระทำไว้ในขั้นตอนเดียวจนสับสน
- ระบุ "ใครเป็นคนทำ" กำกับไว้ถ้ามีมากกว่า 1 บทบาทเกี่ยวข้อง
- แทรกจุดตัดสินใจเป็นรูปแบบเงื่อนไขชัดเจน (ถ้า A → ไปข้อ X, ถ้า B → ไปข้อ Y)
- แทรกคำเตือน/ข้อควรระวังไว้ตรงจุดที่เกี่ยวข้อง ไม่ใช่รวมไว้ท้ายเอกสารเพียงที่เดียว

### 4. เพิ่มส่วนสนับสนุนให้เอกสารสมบูรณ์
เติมส่วนที่ SOP มาตรฐานควรมี แม้ผู้ใช้ไม่ได้พูดถึงตรงๆ:
- วัตถุประสงค์ของ SOP นี้ (ทำไมต้องมีขั้นตอนนี้)
- ขอบเขตงาน (scope) — ใช้กับสถานการณ์ไหนบ้าง ไม่ครอบคลุมกรณีไหน
- อุปกรณ์/เอกสาร/ระบบที่ต้องเตรียมก่อนเริ่ม
- เกณฑ์ตรวจสอบว่าทำถูกต้อง (quality check)
- สิ่งที่ต้องทำเมื่อเกิดข้อผิดพลาดหรือกรณีพิเศษ (exception handling)

### 5. ตรวจทานความสมบูรณ์ก่อนส่งมอบ
อ่านทวนว่าคนที่ไม่เคยทำงานนี้มาก่อนสามารถทำตามเอกสารแล้วได้ผลลัพธ์ที่ถูกต้องหรือไม่ ตัดคำศัพท์เฉพาะภายในองค์กรที่คนนอกทีมอาจไม่เข้าใจออก หรืออธิบายเพิ่มในวงเล็บ

## โครงสร้าง Output

```
# SOP: [ชื่อกระบวนการ]
รหัสเอกสาร: [ถ้ามี เช่น SOP-OPS-001] | เวอร์ชัน: 1.0 | วันที่จัดทำ: [DD/MM/YYYY]
ผู้จัดทำ: [ชื่อ/ตำแหน่ง] | แผนก/ทีมที่เกี่ยวข้อง: [ระบุ]

## วัตถุประสงค์
[อธิบายสั้นๆ ว่า SOP นี้มีไว้ทำไม แก้ปัญหาอะไร]

## ขอบเขต
- ใช้กับ: [สถานการณ์ที่ครอบคลุม]
- ไม่ครอบคลุม: [กรณีที่ต้องใช้ SOP อื่นแทน ถ้ามี]

## ผู้เกี่ยวข้อง
| บทบาท | หน้าที่ความรับผิดชอบ |
|---|---|
| [ตำแหน่ง 1] | [สรุปหน้าที่] |
| [ตำแหน่ง 2] | [สรุปหน้าที่] |

## สิ่งที่ต้องเตรียมก่อนเริ่ม
- [เครื่องมือ/ระบบ/เอกสาร ข้อ 1]
- [เครื่องมือ/ระบบ/เอกสาร ข้อ 2]

## ขั้นตอนการทำงาน
1. **[ผู้รับผิดชอบ]** [การกระทำที่ต้องทำ]
2. **[ผู้รับผิดชอบ]** [การกระทำที่ต้องทำ]
   - หากพบ [เงื่อนไข A] → [ไปทำสิ่งนี้ / ข้ามไปข้อ X]
   - หากพบ [เงื่อนไข B] → [ไปทำสิ่งนี้ / ข้ามไปข้อ Y]
3. ...
n. [ขั้นตอนสุดท้าย/การปิดงาน]

## จุดตรวจสอบคุณภาพ
- [ ] [เกณฑ์ที่บ่งบอกว่าขั้นตอนนี้ทำถูกต้อง]
- [ ] [เกณฑ์ข้อถัดไป]

## กรณีพิเศษ/ข้อผิดพลาดที่พบบ่อย
| สถานการณ์ | สิ่งที่ควรทำ |
|---|---|
| [กรณีพิเศษ 1] | [วิธีจัดการ] |

## สมมติฐานที่ควรยืนยันกับผู้จัดทำ
- [ระบุจุดที่ skill เดาเอาจากบริบท ควรให้เจ้าของกระบวนการยืนยันอีกครั้ง]
```

## ตัวอย่าง

**Input (คำพูดของผู้ใช้แบบไม่เป็นทางการ):** "พอลูกค้าสั่งของทางไลน์ พนักงานก็เช็คสต็อกในระบบก่อน ถ้ามีของก็คีย์ออเดอร์ ถ้าไม่มีก็แจ้งลูกค้าว่าของหมด แล้วเสนอสินค้าใกล้เคียงแทน พอคีย์ออเดอร์เสร็จก็ส่งให้แผนกแพ็คของ แพ็คเสร็จค่อยแจ้งขนส่งมารับ"

**Output คร่าวๆ ที่ควรได้:**
- ชื่อ SOP: "SOP: กระบวนการรับออเดอร์ลูกค้าทางไลน์และส่งต่อแผนกแพ็คสินค้า"
- ขั้นตอนที่แปลงแล้ว เช่น
  1. **พนักงานรับออเดอร์** ตรวจสอบสต็อกสินค้าที่ลูกค้าสั่งในระบบสต็อก
     - หากมีสินค้าเพียงพอ → ไปข้อ 2
     - หากสินค้าหมด → แจ้งลูกค้าทางไลน์ว่าสินค้าหมด และเสนอสินค้าทดแทนที่ใกล้เคียง
  2. **พนักงานรับออเดอร์** คีย์ออเดอร์เข้าระบบให้ครบถ้วน (ชื่อลูกค้า สินค้า จำนวน ที่อยู่จัดส่ง)
  3. **พนักงานรับออเดอร์** ส่งข้อมูลออเดอร์ต่อให้แผนกแพ็คสินค้า
  4. **แผนกแพ็คสินค้า** แพ็คสินค้าตามรายการในออเดอร์ และตรวจสอบความถูกต้องก่อนปิดกล่อง
  5. **แผนกแพ็คสินค้า** แจ้งขนส่งให้เข้ามารับพัสดุ
- ส่วน "สมมติฐานที่ควรยืนยัน" จะระบุ เช่น "ยังไม่ระบุว่าใครเป็นคนตรวจสอบคุณภาพก่อนส่ง ควรยืนยันกับเจ้าของกระบวนการ"

## เกณฑ์คุณภาพ

- [ ] ทุกขั้นตอนขึ้นต้นด้วยคำกริยาการกระทำ และระบุผู้รับผิดชอบชัดเจน
- [ ] มีการจัดการจุดตัดสินใจ (if/then) แยกออกจากลำดับหลักอย่างชัดเจน
- [ ] ครอบคลุมส่วนสนับสนุนครบ (วัตถุประสงค์ ขอบเขต การเตรียมตัว จุดตรวจสอบคุณภาพ)
- [ ] ภาษาที่ใช้เข้าใจง่าย คนที่ไม่เคยทำงานนี้มาก่อนอ่านแล้วทำตามได้จริง
- [ ] ระบุสมมติฐาน/จุดที่ต้องยืนยันแยกไว้ต่างหาก ไม่ปะปนกับขั้นตอนจริง
- [ ] ไม่เพิ่มขั้นตอนที่ผู้ใช้ไม่ได้เล่ามาโดยไม่มีเหตุผลรองรับ
