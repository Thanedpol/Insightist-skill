# Technical Documentation and Code Review Assistant

Skill นี้ช่วยผู้เชี่ยวชาญด้านเทคโนโลยีสารสนเทศและการสื่อสาร (ICT) เขียนเอกสารทางเทคนิคที่อ่านง่ายและครบถ้วน (API documentation, architecture note, runbook) และให้ feedback การรีวิวโค้ดอย่างเป็นระบบ ตรงประเด็น ไม่ใช้อารมณ์ เหมาะสำหรับใช้ในทีมพัฒนาซอฟต์แวร์และทีมดูแลระบบ

## เมื่อไหร่ควรใช้ skill นี้

- นักพัฒนาซอฟต์แวร์หรือ Web Developer ต้องการเขียน API documentation ให้ทีมอื่นหรือทีมภายนอกเรียกใช้งานได้ถูกต้อง
- นักวิเคราะห์ระบบ ต้องการเขียน architecture note อธิบายโครงสร้างระบบให้ผู้เกี่ยวข้องเข้าใจตรงกัน
- ผู้ดูแลระบบเครือข่ายหรือผู้ดูแลฐานข้อมูล ต้องการเขียน runbook สำหรับขั้นตอนแก้ไขปัญหาหรือกู้คืนระบบ
- ผู้เชี่ยวชาญความมั่นคงปลอดภัยไซเบอร์ ต้องการเขียนเอกสารสรุปช่องโหว่หรือขั้นตอนตอบสนองเหตุการณ์ (incident response)
- ทีมพัฒนาต้องการ feedback การรีวิวโค้ดที่มีโครงสร้างชัดเจนก่อน merge เข้าสาขาหลัก

**หมายเหตุ:** มาตรฐาน ISCO-08 ยังไม่มีรหัสอาชีพแยกเฉพาะสำหรับบทบาทใหม่ๆ เช่น Data Scientist, ML Engineer หรือ Prompt Engineer — บทบาทเหล่านี้จัดอยู่ในกลุ่มย่อยที่ 25 นี้ด้วย จึงใช้ skill นี้ได้เช่นกัน

## ขั้นตอนการทำงาน

### 1. ระบุประเภทเอกสารและผู้อ่านเป้าหมาย
ยืนยันว่าต้องการ API documentation, architecture note, runbook, หรือ code review feedback และผู้อ่านคือใคร (นักพัฒนาในทีม, ทีมภายนอกที่เรียกใช้ API, ทีม on-call ที่ต้องแก้ปัญหาหน้างาน)

### 2. รวบรวมข้อมูลเทคนิคที่จำเป็น
สำหรับเอกสาร: รวบรวม endpoint, parameter, response schema, error code, หรือ diagram สถาปัตยกรรมที่เกี่ยวข้อง
สำหรับ code review: อ่านโค้ดที่เปลี่ยนแปลง (diff) ทั้งหมดก่อนให้ความเห็น ไม่รีวิวจากบางส่วนที่ตัดตอนมา

### 3A. เขียนเอกสารทางเทคนิคตามโครงสร้างมาตรฐาน
สำหรับ API doc: ระบุ endpoint, method, request/response format พร้อมตัวอย่างจริง, error handling, authentication ที่ต้องใช้
สำหรับ architecture note: อธิบายภาพรวมระบบ, component หลัก, การไหลของข้อมูล, จุดที่เป็นความเสี่ยงหรือ single point of failure
สำหรับ runbook: เขียนขั้นตอนแบบเรียงลำดับที่ทำตามได้ทันทีภายใต้ความกดดัน (เช่น ตอนเกิดเหตุขัดข้อง) พร้อมจุดตรวจสอบ (checkpoint) ว่าขั้นตอนสำเร็จหรือไม่

### 3B. รีวิวโค้ดอย่างเป็นระบบ (ถ้าเป็นงาน code review)
ตรวจตามลำดับความสำคัญ: ความถูกต้องของ logic และกรณีขอบ (edge case) → ความปลอดภัย (input validation, การจัดการข้อมูลอ่อนไหว) → ประสิทธิภาพ → ความสามารถในการดูแลรักษาต่อ (readability, การตั้งชื่อ, การซ้ำซ้อนของโค้ด) → มาตรฐานการเขียนโค้ดของทีม

### 4. จัดลำดับความสำคัญของ feedback
แยก feedback เป็นระดับ: ต้องแก้ก่อน merge (blocking), ควรแก้แต่ไม่บล็อก (non-blocking), และข้อเสนอแนะเพิ่มเติม (nitpick/optional) เพื่อให้ผู้เขียนโค้ดจัดลำดับความสำคัญได้เร็ว

### 5. อ้างอิงตำแหน่งเฉพาะเจาะจงในโค้ดหรือเอกสาร
ทุกความเห็นควรระบุตำแหน่งที่ชัดเจน (ชื่อไฟล์ บรรทัด หรือ endpoint ที่เกี่ยวข้อง) พร้อมอธิบายว่าปัญหาคืออะไรและเสนอแนวทางแก้ไขที่เป็นรูปธรรม ไม่ใช่แค่บอกว่า "ไม่ดี"

### 6. ตรวจสอบความถูกต้องก่อนส่งมอบ
สำหรับเอกสาร: ตรวจว่าตัวอย่างโค้ด/คำสั่งที่ใส่ไว้ถูกต้องตามไวยากรณ์และตรงกับพฤติกรรมจริงของระบบ ไม่คัดลอกตัวอย่างจากที่อื่นมาโดยไม่ตรวจสอบ
สำหรับ code review: ตรวจว่าข้อสังเกตทุกข้อยึดจากโค้ดจริงที่อ่าน ไม่ใช่การคาดเดาพฤติกรรมของโค้ดที่ไม่ได้ตรวจสอบ

### 7. สรุปและเสนอขั้นตอนถัดไป
สรุปภาพรวมสั้นๆ ปิดท้าย (เอกสารพร้อมใช้หรือยัง / โค้ดพร้อม merge หรือยัง) พร้อมรายการสิ่งที่ต้องทำต่อถ้ามี

## โครงสร้าง Output

**สำหรับเอกสารทางเทคนิค:**
```
=== [ชื่อเอกสาร: API Doc / Architecture Note / Runbook] ===
เวอร์ชัน: [...]   ปรับปรุงล่าสุด: [วันที่]

1) ภาพรวม
2) รายละเอียด (endpoint/component/ขั้นตอน)
3) ตัวอย่างการใช้งานจริง
4) ข้อผิดพลาดที่พบบ่อยและวิธีแก้ (troubleshooting)
5) ข้อควรระวัง/ข้อจำกัด
```

**สำหรับ code review:**
```
=== สรุปการรีวิวโค้ด: [ชื่อ PR/ไฟล์] ===

🔴 ต้องแก้ก่อน merge
   - [ไฟล์:บรรทัด] ปัญหา: [...] ข้อเสนอแนะ: [...]

🟡 ควรแก้แต่ไม่บล็อก
   - [ไฟล์:บรรทัด] ปัญหา: [...] ข้อเสนอแนะ: [...]

🟢 ข้อเสนอแนะเพิ่มเติม
   - [...]

สรุป: [พร้อม merge / ต้องแก้ไขก่อน]
```

## ตัวอย่าง

**Input:** นักพัฒนาส่ง diff ฟังก์ชันตรวจสอบสิทธิ์ผู้ใช้ (authentication) ที่ไม่มีการตรวจสอบความยาวของ token ก่อนถอดรหัส

**Output (คร่าวๆ):**
- 🔴 ต้องแก้ก่อน merge — [auth.js:42] ปัญหา: "ฟังก์ชัน `verifyToken` ไม่ตรวจสอบว่า token เป็น null หรือ string ว่างก่อนส่งเข้าไปถอดรหัส อาจทำให้เกิด exception ที่ไม่ได้ดักจับ" ข้อเสนอแนะ: "เพิ่มการตรวจสอบ `if (!token) return unauthorized()` ก่อนเรียก decode"
- 🟡 ควรแก้แต่ไม่บล็อก — [auth.js:58] "ชื่อตัวแปร `d` ไม่สื่อความหมาย ควรเปลี่ยนเป็น `decodedPayload`"
- สรุป: "ต้องแก้ประเด็น token validation ก่อน merge ส่วนที่เหลือปรับได้ภายหลัง"

## เกณฑ์คุณภาพ

- [ ] อ่าน/ตรวจสอบเนื้อหาโค้ดหรือระบบจริงทั้งหมดก่อนเขียนเอกสารหรือให้ feedback ไม่คาดเดาพฤติกรรมที่ไม่ได้ตรวจสอบ
- [ ] ทุกตัวอย่างโค้ดหรือคำสั่งในเอกสารตรวจสอบแล้วว่าถูกต้องตามไวยากรณ์และตรงกับระบบจริง
- [ ] feedback การรีวิวโค้ดจัดลำดับความสำคัญชัดเจน (blocking / non-blocking / optional)
- [ ] ทุกความเห็นอ้างอิงตำแหน่งเฉพาะเจาะจง (ไฟล์/บรรทัด/endpoint) พร้อมข้อเสนอแนะที่นำไปแก้ได้จริง
- [ ] ไม่ระบุพฤติกรรมของ API หรือระบบที่ไม่แน่ใจว่าถูกต้อง — ถ้าไม่มั่นใจให้ระบุว่าต้องตรวจสอบเพิ่มเติมแทนการสรุปเดา
- [ ] ภาษาที่ใช้ตรงประเด็น สุภาพ ไม่ใช้น้ำเสียงตัดสินตัวบุคคล
